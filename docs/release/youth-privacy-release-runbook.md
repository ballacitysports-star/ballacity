## Status vocabulary (used throughout this runbook)

Four separate states. A later state is never implied by an earlier one, and none is claimed without the evidence named here.

| State                   | Meaning                                                                                                                                     | Evidence                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Implemented**         | code, migration and tests exist on a branch or pull request and pass in a local or CI replay                                                | pull request number and final-head CI run               |
| **Merged**              | the change is in `main`. Merging applies nothing: Lovable syncs code, migrations are applied by hand, publishing is separate                | merge commit on `main`                                  |
| **Deployed**            | the migration has been applied to the production database (ledger row present) and the application build containing the change is published | ledger row and published build id, recorded at the time |
| **Production-verified** | the read-only checks in sections 3, 7 and 12 have been run against production after deployment and matched                                  | dated query results, aggregates only                    |

State on 2026-11-04: every privacy change is **Implemented** only (open pull requests). Documentation, tests and repository governance are **Merged**. Nothing in this runbook is **Deployed** or **Production-verified**. Production is NO-GO.

## 0. Principles

1. Production is never a test environment. Everything is rehearsed first in a verified, isolated Supabase project.
2. Migrations are applied by hand, one file at a time, in the order below, each in its own transaction, each followed by
   read-only verification. There is no "apply all".
3. Exact youth-game locations are never restored into broadly readable columns, at any step, for any reason. Failure
   handling moves forward (fix, or switch features off in the app), never back into exposure.
4. Stop conditions: any unexpected row count, any verification mismatch, any grant not exactly as listed. Stop, do not improvise.

Roles x cohorts, each with at least one positive and one negative:

- **Minor (13-15, 16-17, under-13), unknown age:** cannot see an exact youth venue unless on the roster with the fee settled; cannot

## 8. Location backfill, validation and coarsening (the last, irreversible step)

Goal: when this section is complete, no account other than the entitled ones can obtain the exact address or coordinates of any youth-inclusive game through any path in section 12. Until it is complete, existing venues stay exactly as exposed as today.

1. **Prerequisites (all before step 3 below).** Migration steps 4 to 9 applied and verified; the application build with PRIV-2C and PRIV-2D live; V1 (private copies = youth-inclusive games, none for adult-only games) and V6 (no youth game holds a place in its public text) both clean. 2. **Adoption window.** Keep the dual-read build (#249) live for at least 7 days. 3. **Activation (one approved maintenance window, steps 3 and 4 back to back).** Needs, all of them: owner approval in writing; the adoption confirmation written into the setting (`"app_adoption_confirmed": "2c-verified"`); the typed session confirmation (`SET app.confirm_activate_youth_coarsening = 'yes'`); V1 passing. 4. **Backfill coarsening** with `coarsen_existing_youth_games(n)` (service role) until it returns 0. ## 9. Failure handling: never back into exposure

- Before activation: any problem -> stop; the switch is still off and nothing was coarsened; fix and re-run.
- After activation: **the switch cannot be turned off and no function restores exact values to public columns, by design.**
  If the app cannot show an exact venue to someone entitled: fix forward (app fix or a targeted private-table correction by the service
  role, each with the owner's approval recorded); as a stopgap show the coarse area and the host's own message. If a private copy is wrong: correct the private row (service
  role, with the owner's approval recorded) and have the host re-confirm; never write exact values into `hosted_games`.
- **Application rollback.** Before activation: rolling the app back to the previous build is safe (public columns are still exact). After activation: roll back **only to a build that is #249 or later**; a pre-#249 build would read the coarse public columns as if they were exact and show every host a coarse venue for their own game (a workflow break, not an exposure). Do **not** use Lovable's "revert to commit" to a point before #249 after activation, and do not let any automated edit revert the app files; if the app breaks, the answer is a forward fix or maintenance mode.
- **A migration fails midway.** Each runs in a transaction, so it leaves nothing half-applied; stop and fix the cause. Never run a rollback script to "get unstuck" without the owner's typed approval and a recorded reason.
- **Verification mismatch after a step.** Do not continue; compare with the rehearsal; fix forward in a new reviewed migration that keeps every protection.
- Payment or join problems: the fixes are additive policies/functions in a new migration; do not run rollback scripts that re-open access.
- Data loss risk: `hosted_game_private` is the only exact record after activation. Back it up (logical dump to restricted storage) before activation and before each batch; restore only the private table, never the public columns.
- **PRIV-2D guard misfires** (a legitimate description refused, or text that should be refused accepted): fix forward in a new migration that edits `private_sec.text_discloses_location` only (the triggers stay). A host who is blocked can describe the area differently or ask a moderator; cancellations are never blocked by the guard. Dropping the triggers re-opens the leak and needs the owner's typed approval (`docs/rollbacks/20261104130000_youth_location_leaks.down.sql` (in #256)).
- **Invitation or notification shows the generic label where the recipient should see more:** by design they see the area only; the exact place is on the game page after an approved, settled participation. Do not widen the invitation text.
- If exposure is suspected at any step (an unentitled account obtained an exact venue): as an explicit emergency exception to the approval rule, turn on maintenance mode, preserve logs, tell the owner immediately, and treat it as a privacy incident before changing anything.

select count(*) from public.hosted_games g
 where not public.game_age_range_is_adult_only(g.min_age,g.max_age)
   and (g.location is distinct from private_sec.coarse_game_label(g.neighborhood)
        or g.lat is distinct from round(g.lat,2) or g.lng is distinct from round(g.lng,2));
-- V3 the exact venue is still readable from the public columns                  (must be 0)
select count(*) from public.hosted_games g join public.hosted_game_private p on p.game_id = g.id

   and p.location is distinct from private_sec.coarse_game_label(g.neighborhood);
-- V4 access shape
select has_table_privilege('anon','public.hosted_game_private','select')                               as anon_select,       -- false
       has_table_privilege('authenticated','public.hosted_game_private','insert,update,delete')          as client_write,      -- false

select count(*) from pg_views where definition ~* 'hosted_game';                                          -- 0

select count(*) from public.availability_contact_requests r

 where r.game_id is not null

   and r.game_location is distinct from private_sec.coarse_game_label(g.neighborhood);

select count(*) from public.list_youth_games_with_location_text();
-- V7 invitation notifications for youth games carry only sport + coarse form                                     (must be 0)
select count(*) from public.notifications n
 join public.hosted_games g on g.id = substring(n.link from '^/games/([^/?#]+)')
 where n.type = 'game_invite' and not public.game_age_range_is_adult_only(g.min_age, g.max_age)
   and n.body is distinct from concat_ws(' · ', nullif(btrim(g.sport), ''), private_sec.coarse_game_label(g.neighborhood));
