## 2. Migrations

Same route as batch 4. Each migration ran as one transaction through Lovable's database tool. The transaction:

1. inserted the ledger row holding the file's text exactly as on `main`;
2. refused unless that text's md5 equalled the file's;
3. ran the stored text with `EXECUTE`.

Each step had a whole-catalog fingerprint pre-check and post-check (`docs/migration-evidence/catalog-fingerprint-cte.sql`).

**Rehearsal.** First, both apply scripts were run locally on a replay of `main` with the two migrations removed, which
is production's starting state. Both landed on the expected fingerprints. A copy with a wrong md5 rolled back with
nothing written: ledger 0, fingerprint unchanged. The first build of the scripts used a dollar-quote tag that started
with a digit (`$405$`), which Postgres rejects. The rehearsal caught it before anything reached production, and the
tags were renamed `ledger_405` and `ledger_408`.

**Read-only facts before applying:** 5 profiles, none with an unknown age; 0 pending payment claims; 0 pending team
invites.

## 3. `sandbox_exec`

**Who uses it.** Lovable's AI agent: its code workspace connects to the production database as this role.

- **Production's statistics** (`pg_stat_statements`, since 2026-10-28) show 11 calls as `sandbox_exec`:
  - `SHOW server_version_num` and `DROP DATABASE IF EXISTS "ballacity_dbtest"`, both from `scripts/db-test.mjs`, so
    the repo's database test script was run against production;
  - the `has_function_privilege(...) AS auth_exec` check in `docs/rls-cohort-verification.md`, which Lovable's bot
    (gpt-engineer-app) wrote.
- **Lovable's own answer.** Asked in plan mode, without changes, Lovable's agent confirmed that its workspace's `PGUSER`
  is `sandbox_exec.<project ref>`. The workspace also holds `PGPASSWORD`, `DB_URL`, `SUPABASE_DB_URL` and
  `SUPABASE_SERVICE_ROLE_KEY`. The published app, its server functions and backend functions use `anon`,
  `authenticated` and `service_role`, not this role.

**Decision.** The role belongs to Lovable, so under step 3 its grants stay as they are. Its login stays disabled
(since 02:20 UTC). Effect: Lovable's agent can no longer run SQL or the repo's scripts directly against production, for
example `psql` or `bun run test:db`. The app is unaffected.

**Still true.** Lovable's workspace holds production's service-role key, which reads and writes every table regardless of
this role. That is how Lovable Cloud works, not something this role adds. If Lovable turns the role's login back on,
`SELECT rolcanlogin FROM pg_roles WHERE rolname = 'sandbox_exec'` will show it.
