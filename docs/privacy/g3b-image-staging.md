## Change in this pull request: stage privately, publish only clean bytes

- Migration `20261106120000_private_image_staging.sql`: a private bucket `image-staging` (8 MB, image types only). A signed-in user may insert only a plain file directly inside their own folder (`{uid}/{file}`, no sub-folders) and read back their own staged files for five minutes after the upload, never one the server has quarantined, removed or held (an own-folder SELECT policy, which Storage's `INSERT ... RETURNING` requires). There is no UPDATE or DELETE for API roles, enforced by RESTRICTIVE policies, and a `BEFORE UPDATE` trigger also refuses the overwrite Storage itself performs for a signed upload URL minted with upsert (RLS does not see that write), so the uploader cannot replace or delete a staged file through the API; promotion, cleanup and the sweeper use the service role. _(Corrected in review round 4: earlier text said there was no SELECT policy, and round 3 had added an own-folder DELETE policy, now removed. Corrected again in the final review: RLS alone did not stop a signed-URL overwrite, and the own-folder SELECT had no time or moderation limit.)_
- `promoteStagedImage` (server): download the staged file, validate type, size and dimensions, strip metadata, scan the **clean** bytes, and only if everything passes write them to the destination bucket, record the outcome, and remove the staged copy. Unsafe files stay in the private bucket (quarantined, escalated if child-safety); invalid files are removed. A failed publish keeps the staged file so a retry works; a retry or concurrent second call after success returns the recorded outcome.
- Client (`uploadDataUrlToBucket`): stage, then promote. **There is no fallback to a direct public upload.** If the staging bucket is missing, staging errors, the folder is not the caller's own, or the user is signed out, the upload fails with a clear message. Deploy order is therefore: migration first, then the app.
- The old direct path is **not** closed here (see the transition plan). After the new build has been live for a full adoption window, a separately approved migration should drop the direct INSERT/UPDATE policies on the public image buckets (avatars/covers: "Users write own avatar"; "Users write entity images in own folder"; org and team owner policies). Until then a direct client can still bypass staging; a read-only sweep (below) detects that.

## Recovery

Forward only. The client has **no** fallback: if the staging bucket is missing it shows "Image uploads are temporarily unavailable", and any other staging or promotion error surfaces to the user while the staged file stays private. _(Corrected in review round 4: earlier text and the migration header described a fallback to direct upload for a missing bucket; the code never had one after round 2.)_ Disabling staging means shipping a client that uploads directly again, which restores the old window; it is not recommended.

Findings that remain, by design, until phase 2:

1. **Direct legacy uploads and in-place overwrite.** The existing public-bucket policies let an owner insert and update objects in their own folder. An older client, or a user calling the Storage API directly, can still put an unprocessed original in a public bucket, or overwrite a finalized image with one. The sweep below finds unfinalized objects; it cannot find an overwrite. Phase 2 removes the write policies.
2. **No per-user staging quota.** A user can fill their own private staging folder up to the platform limits; the sweeper bounds the retention, not the rate.
3. **CDN behaviour** after replacement or deletion is only verifiable in the sandbox (ST-8.5).

Phase 2 is prepared as `supabase/phase2/g3b_phase2_close_direct_image_uploads.sql`, **outside** `supabase/migrations` so that nothing replays, syncs or applies it. It refuses to run without the staging bucket and its upload policy. It drops every browser INSERT/UPDATE path into `avatars`, `covers`, the org, team and trainer image buckets, and `game-covers`. It keeps owner read-back and delete (and, since the round 4 corrections, adds own-folder read-back of entity images so their owners can delete them), then asserts by allow-list that every remaining API-role write policy is pinned to a non-image bucket. Test `445_image_phase2_direct_upload_closure.test.sql` applies it inside a rolled-back transaction: 15 assertions at round 4 (10 of them fail without the script), 32 after the round 4 corrections (own-folder entity images and the allow-list postcondition with its negative controls). The test proves old clients are refused, in-place overwrites are refused, staging and the service-role promotion still work, owners and team or org admins can still read and delete their own images, and the attachment, payment-proof, highlight-video and staging policies are unchanged. To ship it, copy it into a new timestamped migration at the time, after re-reading the policy names from the target. Since the final review the postcondition also counts policies granted to any role that `anon` or `authenticated` inherits (`pg_has_role(..., 'MEMBER')`), not only the literal role names.

Endpoints to retire with phase 2 (they exist only for older clients that upload straight into a public bucket): `finalizeImageUpload` (`src/lib/image-uploads.functions.ts`, logic in `src/lib/image-finalize-direct.server.ts`). Once the direct write policies are gone it has nothing legitimate to finalize; remove it in the same release, after the adoption window. Until then it refuses objects already quarantined or removed and fails closed when the scan cannot run (final review, M3).

None of these is location or camera metadata, but each can carry hidden data through a published image. Recommendation: re-encode every published image with `sharp` (decode, re-encode, attach only a standard sRGB/Display P3 profile).
