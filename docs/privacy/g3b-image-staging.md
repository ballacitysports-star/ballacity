# G3b: private staging for image uploads (review of #258 and its follow-up)

Status: **implemented locally, open in a pull request (stacked on #258). Not merged, not applied to production, not verified in production.**

## Review of #258: is an unprocessed original ever publicly reachable?

| Question                                                                           | Finding                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Direct client upload to a public bucket (avatars, covers, team/org/trainer images) | **Yes, a window exists.** The browser writes the original to the public bucket, then calls `finalizeImageUpload`, which cleans the file in place. Until that call completes, the original (GPS and camera data included) is served at its public URL. The path holds a random UUID, so it is hard to guess, but it is not access-controlled.                                                     |
| Failed or skipped finalization                                                     | **The window can be permanent.** If the network drops, the tab closes, or a client calls the storage API directly and never calls the server, the original stays public. Nothing server-side requires an uploaded file to have been finalized before a profile or listing points at it. (In production today every image object has a moderation record, i.e. was finalized; see the inventory.) |
| Retries and concurrent finalization                                                | Safe: cleaning an already clean file is a no-op, and the in-place rewrite is a single object replace, so a reader sees either the original or the clean file, never a partial one.                                                                                                                                                                                                               |
| Large images                                                                       | Files up to 8 MB are cleaned in memory; scans over 4 MB use a signed URL. A file that cannot be cleaned is removed and the upload refused (fail closed). Not measured on the real platform: worker memory and time limits (sandbox item).                                                                                                                                                        |
| CDN caching of the replaced object                                                 | Unverified locally. The original was uploaded with a one-year cache header; whether the edge serves a stale original after the in-place replacement depends on the platform's purge behaviour. Only the sandbox can show it. This is a second reason not to publish originals at all.                                                                                                            |
| Message attachments                                                                | Private bucket; read only by conversation participants; a message cannot reference an attachment until it is checked (`messages_require_checked_attachment`); #258 strips metadata first. The only people who could fetch an unprocessed file are the participants, and only if they know the random path. No public exposure.                                                                   |
| Derived images and thumbnails                                                      | Generated by the platform's image transformation from the stored object, so they derive from the clean file whenever the first request happens after cleaning. A derivative requested before cleaning would require knowing the URL. With staging there is nothing to request.                                                                                                                   |
| Authorization during processing                                                    | The server checks that the path is in the caller's own folder and that the bucket is known; quarantined images are hidden app-wide by `blocked_image_paths`. A quarantined public object is still fetchable by direct URL (existing behaviour); with staging an unsafe file is never copied to a public bucket.                                                                                  |

## Change in this pull request: stage privately, publish only clean bytes

- Migration `20261106120000_private_image_staging.sql`: a private bucket `image-staging` (8 MB, image types only). A signed-in user may insert only into their own folder; there is no SELECT, UPDATE or DELETE policy, so nobody can read, replace or delete a staged file through the API. Only the service role can.
- `promoteStagedImage` (server): download the staged file, validate type, size and dimensions, strip metadata, scan the **clean** bytes, and only if everything passes write them to the destination bucket, record the outcome, and remove the staged copy. Unsafe files stay in the private bucket (quarantined, escalated if child-safety); invalid files are removed. A failed publish keeps the staged file so a retry works; a retry or concurrent second call after success returns the recorded outcome.
- Client (`uploadDataUrlToBucket`): stage, then promote. It falls back to the old direct flow only when the staging bucket does not exist (database not migrated yet) or the destination folder is not the caller's own, so every existing flow keeps working during rollout.
- The old direct path is **not** closed here. After the new build has been live for a full adoption window, a separately approved migration should drop the direct INSERT/UPDATE policies on the public image buckets (avatars/covers: "Users write own avatar"; "Users write entity images in own folder"; org and team owner policies). Until then a direct client can still bypass staging; a read-only sweep (below) detects that.

Sandbox remediation plan (no production bulk rewrite):

1. In the verified sandbox, load synthetic images with GPS/EXIF in every bucket (`scripts/generate-exif-fixtures.py`), run the assessment, then the rewrite, and confirm counts drop to zero, the pictures still render, and the CDN no longer serves the original after replacement.
2. Compare production's counts (assessment only) with the sandbox; with 32 objects, the production rewrite is a small, reviewable, reversible-by-backup operation, but it needs its own written approval and a backup of the originals to private storage first.
3. Periodic read-only sweep after rollout: public-bucket objects with no moderation record (query above) should stay at zero; any hit means a client bypassed finalization.

## Recovery

Forward only. If promotion fails in the field, the client falls back only for a missing bucket; other errors surface to the user and the staged file stays private. Disabling staging means shipping a client that uploads directly again, which restores the old window; it is not recommended.
