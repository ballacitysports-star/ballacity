# Image runtime for SEC-6 re-encoding: evaluation and proof of concept

Status: **proof of concept on branch `claude/image-runtime-poc` (based on `claude/sec6-image-reencode` at af9ec4fa, PR #282). Nothing deployed. No Cloudflare or Supabase account, binding, bucket or service was created, configured or called. The app is not switched over: `IMAGE_RUNTIME` exists as a seam that defaults to `disabled` and is not read by any call site.** The runtime choice is the owner's; this document gives the evidence and a recommendation only.

## The problem

PR #282 re-encodes every published image with sharp (`src/lib/image-reencode.server.ts`): decode to raw pixels, apply the EXIF orientation, convert to sRGB with no ICC, quantise the colour under transparent pixels, encode a new JPEG/PNG/WEBP from the pixels alone, refuse animation, unsupported formats and anything over 30 MP, and produce a scan-only alpha-removed rendition. The output is verified with the byte inspector, scanned, and exactly those bytes are published.

sharp is native (libvips) and does not load in the Cloudflare Worker that serves the app (`wrangler.jsonc`, `nodejs_compat`). On the current deployment every promotion would be held ("unavailable") and every legacy direct upload refused: no image uploads at all. Two runtimes were evaluated:

- **A. Cloudflare Images binding** (`env.IMAGES`) inside the Worker.
- **B. A minimal Node service running sharp** (the existing `reencodeImage`, unchanged), called by the Worker.

**Local mode verified (level "local").** Your belief is correct: the offline mode is sharp. Read in miniflare's source and observed by running the real Wrangler 4.130.0 local mode in this sandbox (`unstable_startWorker` with an `images` binding; nothing remote):

- it is `sharp(buffer, {})` with defaults: **no EXIF auto-orientation** (a JPEG with orientation 6 came back 120×80, unrotated, tag dropped) — unlike documented production;
- only `rotate`, `width`, `height` are honoured; **`flip` is silently ignored**; `quality` and `anim` are not forwarded (JPEG at sharp's default q80, WebP lossy q80 even when `quality: 100` asks for lossless; animated input → first frame);
- `rgb`/`rgba` output → error 9520 "RGB/RGBA output is not supported in local mode"; GIF output → 9520;
- `.info()` has no frame count and **accepted a 49 MP PNG** (no pixel limit); garbage input → 9523;
- a Display P3 JPEG came back sRGB with no ICC (sharp's default);
- **the colour under alpha 0 survived** in a plain PNG output (`[200,50,10,0]` in, same out), i.e. the hidden-colour issue exists there.

The local-mode fake in the tests is a port of that source. Running the PoC against the **real** local mode and against the fake on 10 inputs (phone JPEG o6, alpha PNG, hidden-alpha PNG, lossy WEBP with alpha, lossless WEBP, opaque WEBP, PNG orientations 2/5/6/7) gave **byte-identical results in all 10** (one-off parity run; not part of the suite because it starts workerd).

## Part B: minimal Node sharp service

### Code (not deployed, no container built)

- `services/image-processor/src/server.ts`: `node:http` server, one route `POST /v1/reencode` (+ unauthenticated `GET /healthz` that reveals nothing). Body = image bytes only (`application/octet-stream`; no user id, path or name). Runs **the existing `reencodeImage` imported from `src/lib/image-reencode.server.ts`** (not copied: the two runtimes cannot drift). Limits: body 8 MB (declared and streamed, checked **before** authentication so an oversized body is never buffered), 30 MP (sharp `limitInputPixels`, inside `reencodeImage`), per-request timeout 20 s (→ 503 `unavailable`; the concurrency slot stays held until the decode really ends), 2 concurrent re-encodes per instance (→ 503), header/request timeouts. Limits can be lowered by environment, never raised above the app's. Refuses to start without a ≥32-byte secret or **with any storage/cloud credential in its environment** (`SUPABASE*`, `SERVICE_ROLE`, `DATABASE_URL`, `PG*`, `AWS_*` keys, `GOOGLE_APPLICATION_CREDENTIALS`, `R2_*`, `CLOUDFLARE_API*`, `*STORAGE*`). No `fetch` or other outbound call anywhere; nothing written to disk; only state is the in-memory nonce cache.
- `src/lib/image-runtime/hmac.ts` (shared, WebCrypto): request HMAC-SHA256 over method, path, millisecond timestamp, 128-bit nonce and body SHA-256; ±60 s skew; nonce single use for 2× the window, recorded **after** the signature check; bounded cache that refuses when full of live nonces. Responses signed over (request nonce, status, body SHA-256).
- `src/lib/image-runtime/node-service-client.ts`: Worker-side client. HTTPS only (loopback HTTP for tests), no redirects, `AbortController` timeout (25 s), response size cap, response signature verified, refusal codes passed through, and the output re-verified in the Worker (type, size, byte inspector). Every transport or service failure → `unavailable` (held).
- `src/lib/image-runtime/processor-protocol.ts`: the wire format (u32 length + JSON metadata + bytes).
- `services/image-processor/Dockerfile`: two stages, **base image digests are placeholders that fail the build until pinned** (`node:22.23.4-bookworm-slim@sha256:…`, `gcr.io/distroless/nodejs22-debian12:nonroot@sha256:…`), `npm ci` from a committed `package-lock.json` (sharp 0.35.4 exact, esbuild 0.25.12 exact), esbuild bundle (verified locally: 37.5 kB, starts, `/healthz` 200, unsigned request 401), non-root UID 65532, distroless (no shell), run with `--read-only --tmpfs /tmp --cap-drop=ALL --security-opt=no-new-privileges` and an internal-only network (documented in the file).

### Failure modes (Node service)

Service down, cold, overloaded or slow → client `unavailable` → promotion holds the upload (nothing published; retry later; legacy direct path refuses). Secret mismatch after rotation → `unavailable` until both sides match (rotate by deploying the service with old+new accepted first: not implemented, an open item). Clock skew > 60 s → 401 → `unavailable`. A compromised service could return a different but clean-looking picture: the Worker re-checks container and metadata but cannot verify the pixels; the scan runs on the returned bytes, so a swapped picture is still scanned (the residual is a service that substitutes pictures, mitigated by isolation: no credentials, no egress, no inbound except from the Worker). Multi-instance replay: the nonce cache is per instance, so a captured request could be replayed to another instance within 60 s; the effect is one extra re-encode of the same bytes, returning the same answer to the attacker, who already had the bytes (no side effects, no storage access).

```
disabled          → every call throws ImageReencodeError("unavailable") → promotion holds, nothing published
cloudflare-images → reencodeImageWithCloudflareImages(bytes, { images: env.IMAGES }); no binding → unavailable
sharp-node        → createImageProcessorReencoder({ url: IMAGE_PROCESSOR_URL, secret: IMAGE_PROCESSOR_SECRET }); misconfigured → unavailable
```

The flow does not change: the server function **reads the original from private staging** with the service key (`image-staging`, as today), passes the bytes to `reencode`, validates the result independently (`promoteStagedImage` already re-checks type, size and dimensions), **scans exactly the returned bytes** (inline under 4 MB, otherwise a server-only `_scan/` copy of those same bytes) and the alpha-removed rendition when present, and **publishes exactly the scanned bytes** with the service key. Neither runtime ever sees a storage credential, a path or a user id; the Node service sees only bytes, Cloudflare Images sees only the stripped bytes. Switching on is two lines (`reencode: selectImageReencoder(env).reencode` at the two call sites) plus the configuration; it was deliberately not done. `selectImageReencoder` reads an explicit env object; on Workers it should be given `process.env` (as the app does for its other secrets) merged with the `IMAGES` binding (`import { env } from "cloudflare:workers"`).

### Deployment complexity

- **CF**: smallest moving-parts count (no new service), but correctness depends on undocumented platform behaviour (raw colour under alpha, JPEG metadata from the binding, rotation direction, determinism) that can only be checked with `wrangler dev --remote` on a real account, and every encoder change on Cloudflare's side is unannounced. Two extra code paths (direct vs pixel) and a hand-written PNG codec to maintain.
- **Node**: one more deployable (image, registry, host, secret rotation, monitoring), but the code that runs is the code that was reviewed and tested in #282, with the same library version, and its behaviour is reproducible locally byte for byte.

### Residual risks

- **CF**: platform behaviours above unverified; images with alpha above 12 MP refused (product change versus #282); 128 MB isolate shared by concurrent requests, so even 12 MP can fail under concurrency (fails closed as `unavailable`/error, nothing published); retries may publish different bytes; local mode cannot validate orientation, quality, lossless WEBP or the `rgba` path; Images is an additional processor of minors' images; the pass-through check refuses a lossy upload that is already byte-identical to the platform's own re-encode (a fixed point; rare).
- **Node**: availability of a separate service (holds uploads when down); secret management and rotation; per-instance nonce cache (replay to another instance within 60 s is harmless, see above); egress denial depends on host configuration; a compromised service can substitute a clean-looking picture (still scanned); base image and sharp/libvips patching cadence.
- **Both**: steganography in pixels (unchanged from #282); the scanner sees only what is published.

### Must be validated on a real account or sandbox before release

Cloudflare Images (with `wrangler dev --remote` or a staging Worker on a test account, not production):

1. `.output({ format: "image/png" })` of PNG/WEBP inputs with alpha: 8-bit RGBA, non-interlaced (the JS decoder refuses interlace and sub-byte grey), colour under alpha 0 either kept or zeroed, never filled with different content.
2. `.output({ format: "rgba" })`: availability, exact layout (headerless RGBA of the oriented size?), whether colour under alpha is preserved; only then consider `pixelSource: "rgba"`.
3. JPEG output from the binding: no APP1/APP2/APP13/COM (the binding has no `metadata` option; the URL default is `copyright`); the allow-list must pass on real outputs (JFIF APP0 is allowed; anything else refuses every upload).
4. WEBP output: no ICCP/EXIF/XMP, VP8X flags; `quality: 100` really lossless (VP8L).
5. Flip/rotate semantics and rotation direction for orientations 2–8 with the PoC's transform table; that **without** an EXIF tag nothing is auto-rotated.
6. ICC: Display P3 and CMYK JPEG converted to sRGB with no embedded profile.
7. `.info()` reports stored (un-oriented) dimensions; error codes for truncated, corrupt and over-100 MP inputs match the mapping.
8. Determinism: same input → same bytes across calls and over weeks.
9. Worker memory and CPU on 12 MP alpha PNGs under realistic concurrency; billing (unique transformations counted per call chain).
10. Plan: Images subscription (not legacy; 9432), Workers Paid CPU limit configured.

Node service (on a sandbox project of the chosen host):

1. Pin both base image digests; build; confirm sharp loads in distroless with the lockfile's `@img/sharp-linux-x64`; run the e2e suite against the deployed URL.
2. Memory and time on a 30 MP JPEG and an 8 MB PNG with the container's limits (1 GiB, 2 vCPU suggested); cold-start time.
3. Read-only root filesystem works (libvips needs no writable temp for buffers; confirm).
4. Egress actually blocked (attempt an outbound connection from the container); ingress restricted to the Worker.
5. Secret rotation procedure; clock sync; 503/timeout behaviour seen as "held" in promotion.
6. Plus everything already listed in `docs/privacy/sec6-image-reencode-quarantine.md` ("Must be validated on a VERIFIED Supabase sandbox"), item 7 in particular.

### Recommendation (for the owner to approve or reject)

**Recommended: the Node sharp service (Part B), hosted on Cloudflare Containers with `enableInternet = false` if that product is acceptable, otherwise Cloud Run with egress denied.** Reasons: it meets every requirement with real-library evidence today (the same `reencodeImage` that #282 reviewed, byte-identical in process), it keeps the 30 MP limit for transparent images, it is deterministic, it costs about two orders of magnitude less per image above the free tier, and local tests are faithful to production. The Cloudflare Images PoC shows the platform _can_ be made to meet most requirements, but only with Worker-side code that re-implements part of the pipeline in JavaScript, a 12 MP ceiling for transparent images, no determinism, and several security-relevant behaviours that are undocumented and cannot be checked locally. Keep `IMAGE_RUNTIME=disabled` (fail closed) until the chosen runtime passes the validation list above.
