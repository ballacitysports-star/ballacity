## Late captures

A capture can complete at PayPal after the request that sent it stopped waiting. Before capturing, the checkout reads
the order (`getOrder`). When PayPal already shows it `COMPLETED` (or lists a capture), the order is never marked
`failed` and the player is never told they weren't charged. It is held in `capturing`, its capture is read with
`getOrderCapture` (no second capture is sent) and checked against the order, the game's current price and payee, and
then `paypal_payment_precondition` is asked as the player. Allowed: recorded as usual. A rule refuses (a host's block,
a payment made another way, ...) or the capture does not match: refunded. The rules cannot be checked: held with its
capture id and reported (`PAYPAL_LATE_CAPTURE_RULES_UNCHECKED`); the player is told support will settle it
(`PAYMENT_HELD_FOR_SUPPORT_MESSAGE`), since nothing re-checks a held order by itself.

When the order cannot be held (another order of the player's for the game is `capturing`, so the one-capture index
refuses it, or the database did not answer) and no other request has taken it, it stays `created` and is reported as
`PAYPAL_LATE_CAPTURE_UNCLAIMED` with its capture id, and the player gets `PAYMENT_HELD_FOR_SUPPORT_MESSAGE`. A superadmin
settles it with the stuck order: `PAYMENT_IN_PROGRESS` does not count a `created` order, so the report is the pointer.

## A payment insert without a clear answer

The insert of the verified `payment_submissions` row can fail in two ways. The database refused it (an error with a
SQLSTATE such as `P0001` or `23514`, or a PostgREST `PGRST` code): its transaction rolled back, nothing was written, and
the capture is refunded. Anything else (a thrown error, a lost connection, which supabase-js reports with an empty
code, a gateway error) may have written the row, so the row is looked for. Found: the payment goes on as recorded. Not
found, or the lookup failed: nothing is refunded (that could give back money for a payment the app holds as verified),
the order is marked `captured` with its capture id and reported (`PAYPAL_PAYMENT_RECORD_UNCONFIRMED`, with the capture
id). The host is notified (PayPal did pay them). The player is not placed on the roster on a guess and is told support
will settle it (`PAYMENT_HELD_FOR_SUPPORT_MESSAGE`). A later capture request for the order finds the row and reports
whether the player is on the roster; it never places them, since a host may have removed them.

## Retries never act twice (PayPal-Request-Id)

PayPal returns the first result for a repeated request that carries the same `PayPal-Request-Id`, for as long as it
keeps the id (see PayPal's API reference for each call).

| Call                         | Request id                                            | Effect                                                                                                                                                                  |
| ---------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Create order                 | `create-<random uuid>`, new for each checkout attempt | A resend after a lost answer returns the same order. A new attempt (the player presses the button again) makes a new order; one nobody approves charges nothing.        |
| Capture (`captureRequestId`) | `capture-<order id>`                                  | The same on every attempt for an order, so an order is captured at most once. A retry of an order PayPal already shows captured sends no capture (see "Late captures"). |
| Refund (`refundRequestId`)   | `refund-<capture id>`                                 | A capture is refunded at most once.                                                                                                                                     |

`postIdempotent` sends each of these once more with the same id when no answer came back at all (the connection
failed or timed out). An answer PayPal did give, success or error, is used as it is and never resent. An error answer
to a capture's resend is never taken as "not captured": it describes the resend, while the first send may still be
capturing (PayPal may answer it with a rate limit or `PREVIOUS_REQUEST_IN_PROGRESS`). The order is held as
`CAPTURE_UNCONFIRMED` and reported instead of released. Order lookups
(`getOrder`, `getOrderCapture`) are reads and carry no id. Every PayPal request has a time limit (10 s for the access
token, 15 s for each other request, `AbortSignal.timeout`), so a hung request ends in the fallback above and is
reported instead of holding the order silently.

## Reading a capture

`parseCaptureResponse` reads the capture itself, never the order: its id, status, amount, currency, PayPal's reason
(`status_details.reason`) and payee (the capture's, else its purchase unit's). It counts captures across all purchase
units; only exactly one is ever used. The checkout records a payment only for a capture whose own status is
`COMPLETED` that matches the amount, currency and payee (the payee confirmed before the capture is used when the
answer omits it). When the capture call gives no usable answer, `getOrderCapture` reads the order's capture from PayPal
the same way, so the amount checked is the captured amount, not the order's.

## Not checked or not covered

- **Not reported:** a request stopped while it holds an order (the server function killed mid-capture) leaves the
  order `capturing` with no capture id and no report. The player sees `CAPTURE_IN_PROGRESS_MESSAGE` and cannot capture
  another order for the game. Until there is a view or report of old `capturing` orders, a superadmin finds these by
  looking for `capturing` orders older than a few minutes.
- **Automatic refunds are unverified for a host's merchant account.** Orders name the host's merchant id as payee, so
  the capture belongs to the host's account. A platform refunding another merchant's capture normally needs that
  merchant's permission and a `PayPal-Auth-Assertion` header; neither exists here (hosts type in a merchant id; no
  partner onboarding). If PayPal refuses, every automatic refund ends as `captured_unrecorded` (safe: reported, other
  orders blocked) and `PAYMENT_REFUNDED_MESSAGE` is never shown. Check a refund against a different payee account in
  the PayPal sandbox before PayPal is turned on.
- Which code PayPal answers a capture resent while the first is still running with is not checked against the
  sandbox. It does not matter for the money: no error answer to a resend releases the order. A first send's 4xx
  outside the excluded codes still releases it when the order shows no capture; only one request can hold an order,
  so no other send of the same capture is running then.
