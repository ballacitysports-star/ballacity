## 1. Unknown age in participation gates

**Defect.** `is_minor()` is false without a birthday, so `team_respond_invite` let an unknown-age account with a guardian link accept without guardian approval, and `child_game_participation_allowed` answered true. `enforce_child_game_participation` checked for a declared age only when the player wrote the row themselves, so a server path (the service role rostering a paid player, `roster-on-payment.server.ts`) rostered an unknown-age account into any game, youth games included. The SEC-1 `org_members` insert policy (`NOT is_minor(user_id)`) let an organization administrator add an unknown-age account.

**Fix (chosen: require a declared age).** Sign-up always collects a date of birth (the root age gate redirects every `unknown` cohort to `/onboarding/age`; `provision_managed_child` requires one), so an unknown age is a legacy account. Treating it as a minor would still let it act wherever no guardian is linked; requiring a declared age closes every path and matches the existing `AGE_VERIFICATION_REQUIRED` rule for a player's own join request.

- `private_sec.child_game_participation_allowed`: false without a declared age.
- `enforce_child_game_participation`: `AGE_VERIFICATION_REQUIRED` for any writer (player, host, guardian, service role), with player-facing or third-party wording.
- `team_respond_invite`: accepting needs a declared age (declining does not).
- `guardian_approve_team_invite`: approving needs the invitee's declared age (a team membership feeds age-dependent rules such as reel audience and messaging).
- `org_members` insert policy: `age_verified(user_id) AND NOT is_minor(user_id)`, the same as `team_members_manager_write`.
- `team_invite_player` needed no change: it already treats anything but `adult` as a minor (no message, guardians notified).

**Behaviour change.** A legacy account without a birthday must add one before joining a game or team (the app's age gate already sends it there). Adults and verified minors are unchanged.

**Tests.** `supabase/tests/531_unknown_age_participation.test.sql` (21): invitation accept and guardian approval refused for unknown age; the service role cannot roster or file a request for one, on a youth or an all-ages game; the org policy; positive controls for adults, a verified 15-year-old (guardian step still required, then approved) and a legacy account after it declares its birthday.

**Open.** None in the database. `age_verified` means "a birthday was declared", not an identity check (unchanged).

## 2. Blank saves on youth-game locations (SEC-1 #6)

**Defect.** After coarsening activation, `sync_hosted_game_private` copied an empty location (and missing coordinates) from an older client into `hosted_game_private`, wiping the only exact copy.

**Fix.** The SEC-1 rule for team facilities and posts now applies to games: for a youth game that stays youth after activation, a blank location, or the coarse label sent back (for the new or the old neighborhood), is not a change and the public column keeps its coarse value; missing coordinates are not a change unless the location itself changed in the same write (a new address that could not be geocoded, whose old point must not be kept). The private copy is updated column by column, so an unchanged column never overwrites the exact value with a coarse one (this also stores a genuine two-decimal pin, the SEC-1 F1-2 case). Paths before activation, on insert, and on a game becoming youth-inclusive are unchanged.

New `public.clear_hosted_game_location(_game text, _fields text[] default {location,lat,lng})`: host only, fields validated, clears the exact copy and the public columns (the text becomes `TBD`, which is what a new game without a location gets, because `hosted_games.location` is NOT NULL), using the batch bypass flag and resetting it. Authenticated and service role only.

Client: in the game edit form an emptied "Venue address" used to keep the old address silently; it now removes the venue through `clearHostedGameLocation` (`src/lib/hosted-games-store.ts`) after the other fields are saved.

**Behaviour change.** A host who empties the address field removes the venue (it reads "TBD"); before, the old address stayed.

**Tests.** `532_youth_game_blank_save.test.sql` (25): blank text, whitespace and null coordinates, and coarse values sent back change nothing; a new address without coordinates and a two-decimal pin are stored; stranger, unknown field and anonymous refused; partial and full clear; bypass flag reset.

**Open.** A host who wants to remove only the map pin has no UI (the RPC supports `ARRAY['lat','lng']`).

## 3. Guardian payee handles on minor-hosted games (PAY-1 #6)

**Defect.** `get_game_host_payment_methods` returned the payee's handles (for a minor-hosted game, a guardian's or organization administrator's Venmo name etc., often a real name) to any signed-in caller for a public listing.

**Fix.** For a game whose host is not a confirmed adult, the public-listing branch no longer applies: only the host, the payee, an approved requester, a participant, the verified guardian of either, or staff (moderator/superadmin) receive handles. A self-made pending request still does not count. Adult-hosted games are unchanged. Because a player must see the handles to pay, a paid minor-hosted game now always requires approval before payment: a new trigger `z_minor_hosted_payment_approval_trg` forces `requires_approval = true` on its payment settings (any writer), and existing rows are brought in line by the migration. The pay flow is therefore request, approval, pay, which the existing client already handles (`games.$gameId.pay.tsx` and `GamePaymentsPanel` call the RPC with the game id).

**Behaviour change.** Paid minor-hosted games can no longer be instant pay-and-join. Payments remain disabled in production (PAY-1).

**Tests.** `533_minor_hosted_payee_handles.test.sql` (20) covers every involved role, the stranger, the pending requester and visitors; payment is refused before approval and accepted after; adult-hosted instant joining and public handles are unchanged. Test 335 gives its payer an approved request (it paid a minor-hosted game without one).

**Open.** `get_host_payment_methods(_host_id)` (no game) is unchanged; it already answers only to someone who paid that payee or is involved with the payee's own games.

## 4. Messaging window extended by date edits (R7 N4)

**Defect.** The host-to-participant game context ended 30 days after `COALESCE(ends_at, date)`, which the host can edit, so moving a finished game's date forward reopened or extended messaging with a minor.

**Fix (chosen: a server-kept anchor).** New server-only table `public.game_contact_windows (game_id, anchor_at)` (row security on, no policies, no client grants), maintained by the definer trigger `zz_track_game_contact_window_trg` on `hosted_games`: the anchor starts at the game's end, follows date edits only while the anchor is still in the future and the game is neither completed nor cancelled, and never moves after that. `private_sec.messaging_connection` uses the anchor (falling back to the game's dates only for a row written with triggers off). Date edits are not refused, so hosts can still correct a past game's record. Existing games are backfilled with their current end (an earlier extension cannot be detected).

**Behaviour change.** Editing the date of an ended, completed or cancelled game no longer changes how long the host can message its participants. Postponing an upcoming game still extends the window to the new date.

**Tests.** `534_game_messaging_window_anchor.test.sql` (14): two successive date edits of an ended game do not restore the context; a postponement keeps it; a completed game's anchor is frozen; clients can neither read nor write the anchors.

**Open.** An upcoming game can be postponed repeatedly before it starts, keeping the context alive (by design: it is still an upcoming game the participant stays on, and the guardian can withdraw them). If that is not acceptable, cap the anchor at, for example, the guardian approval time plus a fixed period.

## 5. Guardian change and team messaging (R7 N5)

**Defect.** After a guardian change the approval on the child's accepted team invitation was given by someone who is no longer a verified guardian, so `team_membership_authorizes` stopped counting it, and `team_invite_player` refused a new invitation with `ALREADY_MEMBER`: the new guardian could not restore it.

**Fix.** `public.guardian_reapprove_team_membership(_team, _child)`: the caller must be a current verified guardian of the child (active and verified link), the child must be a non-adult member with an accepted invitation and not locked. It re-stamps that invitation's `guardian_approved_at/by` in place (the membership is untouched), writes a `family_audit_log` row (`team_membership_reapproved`, with the team, invitation and the previous approver) and notifies every current verified guardian of the child. It returns `approved`, or `already_approved` without writing anything. `public.guardian_team_reapprovals()` lists the caller's children's memberships waiting for it. The Guardian page has a new card, "Teams waiting for your approval" (`src/components/youth/GuardianTeamReapprovals.tsx`), with an Approve button.

**Behaviour change.** New guardian action only; nothing existing changes.

**Tests.** `535_guardian_team_reapproval.test.sql` (26): the defect (context gone, `ALREADY_MEMBER`); a stranger, the former guardian, an unverified guardian link, the child, the coach and visitors are refused; a team the child is not on is refused; the new guardian restores the context, with the audit row and notifications (not to the former or unverified guardian); the second call is a no-op.

**Open.** A membership that was not made through an invitation (a legacy direct roster row) cannot be re-approved (`NO_ACCEPTED_INVITE`); the team removes and re-invites the player. The new guardian is not proactively notified when the link is created; the card appears on their Guardian page.

## 6. Held text for moderators (SEC-1 #2)

**Defect.** The moderation screen showed no held text, so Restore text or Confirm removal was decided blind.

**Fix.** `listReports` (`src/lib/moderation.functions.ts`, moderator-checked) loads, for the held location reports on the page, the latest open automatic hold from `location_report_evidence` through `loadHeldEvidence` (`src/lib/moderation.server.ts`): it checks the moderator role itself and reads with the moderator's own session, so the table's row security (moderators and administrators only) applies as a second check. The report detail (`src/routes/admin.moderation.tsx`) shows each non-empty field (title, description, neighborhood, rules, equipment, cancellation notes and reason) with the hold time, next to the Restore/Confirm buttons. The evidence is part of the moderator report only; nothing a host or reporter receives includes it (their table access is already refused, tests 390, 470, 476).

**Tests.** `src/lib/moderation-evidence.test.ts` (5): latest open hold per game (released holds and moderator removals ignored), field list, a non-moderator is refused before any read, the query filters, no read when nothing is held.

**Open.** Team-post evidence (moderator removals, always already decided) is not shown; there is no open hold for posts.

## 7. Account purge and image-staging (G3b L1)

**Defect.** Account deletion did not remove the account's staged uploads in the private `image-staging` bucket.

**Fix.** `purgeImageStaging` in `src/lib/account-purge.server.ts`, called by `purgeUserAccount` before the auth user is deleted: lists `image-staging/{userId}/` (paged, files only), looks up `image_moderation`, and removes every file except those with status `quarantined` (held as evidence; the row keeps it findable and its `owner_id` becomes NULL with the account), then removes the moderation rows of the removed files. If the hold lookup fails nothing in staging is removed (fail closed) and deletion proceeds like the other buckets; such leftovers are not held, so the existing staging sweep removes them. The change is self-contained (one new exported function and one call) so it merges cleanly with other purge work.

Data export: not extended. The export contains account data, not stored files from any bucket; staged originals are transient (minutes) or held evidence, which is not exported.

**Tests.** `src/lib/account-purge-staging.test.ts` (4): the own folder is listed; non-held files and their rows are removed, a quarantined file is kept, sub-folders are skipped; nothing is removed when the hold lookup fails; a missing bucket is a no-op.

**Open.** "Legal hold" has no separate representation; `quarantined` is the only hold status today. A retention rule for quarantined originals of deleted accounts still needs a legal decision (G3b L1).
