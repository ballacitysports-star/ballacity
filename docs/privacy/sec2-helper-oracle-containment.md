# SEC-2: helper functions are not oracles about other people (containment proposal)

Status: **implemented locally, open in a pull request based on `main`. Not merged, not applied to production, not verified in production.** It is independent of the open privacy stack and is the separately reviewable containment for a gap that exists in production today.

## The production gap (read-only check, 2026-11-05)

All 29 functions below exist in production as `SECURITY DEFINER` and are executable by every signed-in account; none is executable anonymously. Each accepts an arbitrary user id, so a signed-in stranger can call them through the API (`/rpc/<name>`) and learn, for any account id: team membership and role, game participation, the guardian relationship, shared teams, conversation participation, blocks, whether the person is a minor, age verification, platform status, roles, entitlements, AI and payment permissions, and the minor-messaging rule outcome for any pair.

`age_verified`, `ai_analysis_allowed`, `blocks_exist_between`, `can_notify`, `child_game_participation_allowed`, `default_profile_visibility_for`, `game_payments_allowed`, `has_entitlement`, `has_role`, `is_conversation_participant`, `is_game_participant`, `is_guardian_of`, `is_gym_admin_text`, `is_managed_account`, `is_minor`, `is_moderator`, `is_org_member`, `is_superadmin`, `is_team_manager`, `is_team_member`, `is_trainer_org_admin`, `is_trainer_org_member`, `minor_messaging_allowed`, `minor_messaging_block`, `minor_messaging_block_reason`, `platform_status`, `shares_team`, `team_role_of`, `trainer_profile_owned_by`.

## The fix, and why it does not break anything

- No helper body and no row-security decision changes. Each function is **moved** to `private_sec` (`ALTER FUNCTION ... SET SCHEMA`). Policies reference functions by OID, so every existing policy keeps calling the original logic; `private_sec` is not exposed by the API.
- A same-named **public SECURITY INVOKER wrapper** answers for everything that calls by name (other functions, server code, the app). It passes its own `current_user` to `private_sec.rpc_probe_denied`. The check is **structural**: when the wrapper runs as the API role itself (`authenticated` or `anon`), the call came straight from a client (PostgREST `/rpc/<name>`, a GraphQL field, or invoker code running for the client). Inside a `SECURITY DEFINER` function `current_user` is that function's owner, so every internal use is unaffected. A direct client call by someone who is **not staff** gets a fixed answer that reveals nothing (`false`, `NULL`, `'private'`, `'not_permitted'`, `'not_permitted:other'`), unless the helper only answers about the caller and the caller is that person.
- **Two-party helpers that reveal the other person's state have no party exemption:** `minor_messaging_block`, `minor_messaging_block_reason`, `minor_messaging_allowed`, `blocks_exist_between`, `shares_team`, `can_notify`. Every direct client call by a non-staff account gets the fixed answer, even when the caller names themselves as one party.
- The service role (no `auth.uid()`), every `SECURITY DEFINER` caller, staff, and a person asking a one-party helper about themselves are unaffected. App call sites: every signed-in-client call asks a one-party helper about the session user, except the payment-review player check noted under Review round 4. `can_notify` (notifications, push) and `blocks_exist_between` (player passport) are asked with the service role from server code. No client calls the `minor_messaging_*` functions.
- The one `SECURITY INVOKER` function that named a helper, the `guard_team_member_role_change()` trigger (it calls `team_role_of`), now calls `private_sec.team_role_of`. No view and no other invoker function calls a helper by name (480 checks this).

## Later migrations that redefine a helper

- **Prefer `CREATE OR REPLACE FUNCTION private_sec.<helper>(...)`** for a new body. It keeps the OID every policy points at, and the public wrapper needs nothing.
- If a migration redefines `public.<helper>` instead (with `CREATE OR REPLACE`, or `DROP` and `CREATE`), it must re-run `SELECT private_sec.wrap_oracle_helpers();`. That copies the new body into the **existing** `private_sec.<helper>` with `CREATE OR REPLACE`, together with the new definition's owner and grants. It never drops the private copy, because about 160 policies depend on these OIDs. It then rebuilds the public wrapper in place and repoints at `private_sec` any policy that was created against the public name.
- A helper counts as wrapped only when `public.<helper>` is `SECURITY INVOKER` and calls `private_sec.rpc_probe_denied`. The `oracle-wrapper` comment survives `CREATE OR REPLACE`, so it is a label, not evidence.
- A redefinition that renames a parameter or changes the return type cannot replace the private copy in place. `wrap_oracle_helpers()` then stops with an error rather than drop the copy the policies use.
- New `SECURITY INVOKER` functions, views and triggers must call `private_sec.<helper>`, not the public wrapper.

## Tests

`supabase/tests/480_helper_oracle_containment.test.sql` (89 assertions). It checks that every helper is wrapped, that the originals moved and are still used by policies, and that no policy, view or invoker function calls a public wrapper. A stranger's direct probes get the safe answer, with and without `request.path`. A GraphQL-style dynamic call of each of the 29 helpers gets its fixed answer. The six two-party helpers give the fixed answer when the caller is a party. Self, staff and the service role get the truth. A manager still reads the roster through row security. A function that calls the helpers by name still works, and the role-change trigger behaves as before. Anonymous still cannot call the helpers. Re-running is a no-op. A `CREATE OR REPLACE` of `public.can_notify` and `public.is_minor` with definer bodies, followed by a re-wrap, is contained again: the probe is denied, the private OIDs are kept, and a definer caller and a policy see the new logic. A drop and recreate of `is_team_member` followed by a re-wrap succeeds. A later policy naming a public helper is repointed. Run against the previous revision of this migration, 37 of these assertions fail and the file then stops on the `is_team_member` drop error. Full SQL suite on this branch: 985 passed, 0 failed.

## Before production (needs separate approval)

1. In the verified sandbox, confirm that `private_sec` is **not** in the API's exposed schemas (Supabase dashboard, API settings) and not on the `authenticator`/`authenticated` search_path. If `private_sec` were exposed, the moved originals would be callable there and the containment would not hold.
2. Confirm that pg_graphql is disabled (`select * from pg_extension where extname = 'pg_graphql'` is empty), or that it does not expose the public wrappers. The wrappers deny a stranger's GraphQL call too, but GraphQL must not become a second API to reason about.
3. Apply with `SET lock_timeout = '5s'`. The moves take a brief lock on each function only.
4. Verify (read-only): 29 functions in `public` are `SECURITY INVOKER` and call `private_sec.rpc_probe_denied`; `select public.is_team_member('<team>', '<someone else>')` through the API as an unrelated test account returns false.

Rollback: forward-fix only (re-creating the public functions with their original bodies would reopen the oracle). Owner decision recorded in the PR.

## Review round 4 corrections

- **F1, re-wrap skipped a redefined helper (High).** The "already wrapped" test was the `oracle-wrapper` comment, which survives `CREATE OR REPLACE`. A later definer redefinition of `public.can_notify` or `public.is_minor` therefore stayed an open oracle. Now a helper counts as wrapped only if `public.<sig>` is `SECURITY INVOKER` and calls `private_sec.rpc_probe_denied`. A redefined body is moved into the existing `private_sec.<sig>` with `CREATE OR REPLACE` (via `pg_get_functiondef`), with its owner, `search_path` and grants. The OID is kept, so policies run the new logic. The public wrapper is then rebuilt in place.
- **F2, re-wrap dropped a policy-dependent copy (High).** Re-wrapping used to `DROP` the old `private_sec` copy, which fails for helpers that policies use (for example after `is_team_member` is dropped and recreated in public). The private copy is now never dropped. The migration header and this document tell later migrations to prefer `CREATE OR REPLACE private_sec.<helper>`, and say that re-running the wrap handles a public redefinition.
- **F3, a party could still learn the other party's state (High).** `minor_messaging_block`, `minor_messaging_block_reason` and `minor_messaging_allowed` revealed the other person's age cohort and guardian controls. `blocks_exist_between` revealed whether the other person blocked you, `shares_team` revealed a hidden minor on your team, and `can_notify` revealed relationship links. These six now deny every direct client call by a non-staff account, party or not, with the same coarse answers as before. The other 23 helpers were reviewed. Each answers only about the named person (`is_guardian_of(me, X)` tells the caller only whether they are the guardian, or whether X is theirs), so the party exemption stays. The app's two `can_notify` calls (`src/lib/notifications.functions.ts`, `src/lib/push.functions.ts`) used the signed-in client. They now ask with the service role, with `_caller` set to the verified session user.
- **F4, the probe check was text-based (Medium).** pg_graphql (`/rpc/graphql`, top-level `graphql.resolve(...)`) would have exposed the STABLE wrappers without matching the path or the statement text. The check is now structural: the wrapper passes `current_user`, and a call is a client call when that is `authenticated` or `anon`. The path and statement-text triggers were removed because the structural check covers every case they covered, and text matching could misfire inside definer code that happens to share a statement. An anonymous caller always gets the fixed answer. `guard_team_member_role_change()`, the only invoker function that named a helper, now calls `private_sec.team_role_of`. No view does. Policies use OIDs, and re-wrapping repoints any later policy created against a public name. The production checklist now requires confirming pg_graphql is disabled or does not expose the wrappers, and that `private_sec` is not an exposed schema.
- **F5, tests.** Covers all of the above (see Tests), including a loop over all 29 signatures and a negative control against the previous revision.
- **Found while checking call sites, not changed here.** `reviewGamePayment` in `src/lib/payments.functions.ts` asks `game_payments_allowed` about the *player* with the host's signed-in client. With this containment the host gets the fixed `false`, and the review fails with "Payment coordination isn't available for this player's account yet." (the earlier text-based check had the same effect). The `enforce_game_payment_cohort` trigger already enforces the player check in the database. Calling it with the service role would let any signed-in account use the server function to probe a player's cohort. Needs a decision before merge: drop the player pre-check and rely on the trigger, or gate it on an existing submission or participation.
