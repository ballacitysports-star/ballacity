# Notifications a member's app can ask for

Migration `20261119120000_can_notify_without_contact_requests.sql` and the app change that ships with it.

## The problem

`createNotificationForUser` took any `type` (up to 64 characters), title, body and `link` (up to 2000 characters) for any recipient `can_notify(caller, target)` allowed. `sendPushToUser` did the same for a push. `can_notify` was true as soon as one `availability_contact_requests` row linked the two people, in either direction, and anyone can send a contact request to anyone whose availability post they can read. So after one contact request, the sender's app could put any words and any link (another site, or a misleading in-app path) in the other person's notifications and on their lock screen. That is a phishing and spoofing channel.

## What changed

- **The app names a type and a row, never words or a link.** `createNotificationForUser` accepts only the allow-listed requests in `src/lib/notification-requests.ts` (a strict zod union, so a `title`, `body` or `link` is refused). Each names a game, a message or an availability post, and, where the sender picks among several people, the recipient.
- **The server checks the row and writes the notification.** `src/lib/notification-plan.server.ts` reads the row with the service role, checks the caller's part in it, picks the recipients the row allows, and writes the title, body and in-app link from stored data. Every link is built from a checked id and must survive `toAppPath` unchanged. One neutral refusal covers every failure.
- **Repeats are trimmed.** The same notification (person, type, link, title and body) is not sent again within 10 minutes (2 for messages, 60 for payment reminders). A host's roster updates are capped at 10 per player per game per hour.
- **Push moves to the server.** `sendPushToUser` is gone. The push for each row goes out from the same server function, through `deliverPush` (minor curfew, delivery log), and now honours the recipient's push preference for that category (`notification_preferences`), as game reminders already did.
- **`can_notify` no longer counts a contact request** (the migration). Nothing in the app asks `can_notify` any more; the remaining clauses (conversation, join request, game) are unchanged.

## Limits and choices for the owner

- **`game_broadcast` keeps the host's note.** A roster update ("running late, court 2") is a host writing to people who joined the host's own game, which they can also message. The server writes the title (`Host update · <game>`) and the link; the note is at most 280 characters and is refused if it contains a URL, `www.` or a domain. If you would rather have no free text at all, the alternative is a fixed set of updates (late, moved, cancelled...).
- **The payment reminder's text is now fixed.** The game-day sheet's "Edit message" for unpaid players is gone; the server's reminder names the fee and the game.
- **`participant_left` cannot be proven after the fact.** Leaving deletes the player's rows, so the server cannot see they were ever on the game. The request only ever reaches that game's host, in the caller's own name, about the host's own game, and repeats are trimmed.
- **A host removing a player from the game page tells them first.** `hostRemoveParticipant` deletes every row that shows the player was on the game, so the notice goes out (awaited) just before the removal. If the removal then fails, the player has a notice for a removal that did not happen; the host sees the error and can retry.
- **Game titles and display names are still the host's and the member's own words** in titles ("Removed from <game>", "Pat joined <game>"). They are not links, and every link is an in-app path.
