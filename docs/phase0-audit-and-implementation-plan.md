## 1. Executive audit summary

**BallaCity is not a prototype. It is a 212k-line production application with an unusually strong database-enforced safety model and an unusually fragile release process.** The right strategy is to stabilise governance, close four verified security holes, and then grow the network features on top of entities that already exist. Nothing in this plan proposes a rebuild.

**What is genuinely strong (verified from source):**

- The database is the enforcement boundary. Every public table has RLS. Minor safety, guardian approval, join gating, payments, follow approval, reel audience and moderation are implemented as triggers and SECURITY DEFINER functions, and 43 SQL test files assert them in CI on every pull request.
- Identity is complete: email and OAuth sign-in, a four-cohort age engine with a private birthday table and a birthday lock, verified guardian links, parental consent state machine, per-child controls, and managed children implemented as real credential-less auth users so that every policy keyed on `auth.uid()` applies to them.
- Pickup games, teams, tryouts, trainers, facilities, listings and claims, reviews, reels, messaging, notifications and three admin consoles all exist with server-side authorization.
- The E2E safety guard refuses to run against production, and the CI redacts output.

**What blocks the network vision today (verified):**

1. **No social layer.** `/feed` is a games list. The only post table is team-scoped. Follows point only at people, and the Follow buttons on team and trainer pages are cosmetic local state that persist nothing. There is no Home or Following feed.
2. **No unified Discover.** Players, Teams, Trainers and Venues each have their own route, search schema and storage key. Games are loaded whole-table to the browser with `select("*")` and filtered by JavaScript haversine.
3. **Entity vocabulary is split three ways.** Trainers are `teams.kind='coach'`, facilities are `trainer_orgs`, and `account_profiles.kind` uses a fourth naming. There is no generic event, business or coach entity.
4. **Governance debt.** Production has drifted from the repo: 71 hand-applied migrations have no ledger row, two merged security migrations are not applied, ten files are committed in both migration folders and replay twice. Lovable pushes to `main` and applies SQL to production outside the pull request flow. E2E has failed on every run for two months. About 55 pull requests are open, including a 25-PR youth-privacy stack that marks production NO-GO.

**Recommended sequencing.** P0 is governance and the four security fixes (about two to three weeks of focused work plus owner approvals for production application). P1 adds the social layer and unified Discover on existing tables. P2 connects games, teams, events and businesses. P3 covers media, AI, analytics and performance. P4 holds monetization and live streaming behind design placeholders only.

**Recommended first implementation task** (section 14): close the `profile_ages` age-oracle and the `user_roles` escalation with one migration, one SQL test file and one small client change, shipped through the existing hotfix runbook pattern. It is small, independent of the open privacy stack, protects minors, and exercises the exact branch, test and release discipline every later task will need.

CI on the current head shows Unit tests, Typecheck & build and Database tests green and E2E red; those results are cited instead. No Postgres server is available in this session, so the SQL replay was not run locally either.

## 3. Existing architecture

### 3.1 Runtime layers

```
Browser (React 19, TanStack Router, TanStack Query, module singleton stores with Supabase realtime)
  │  server functions (createServerFn, 383 call sites) with bearer attacher
  ▼
Cloudflare Worker (TanStack Start / Nitro, src/server.ts)
  ├─ requireSupabaseAuth → per-request RLS client (user JWT)
  ├─ supabaseAdmin (service role) in *.server.ts only
  ├─ /api/public/* workers: reels/process, notifications/flush, payments/release-holds (worker secret), payments/webhook (Stripe signature), og (public), content-studio/meta-callback
  ├─ /mcp, /.mcp/*, /.well-known/* (@lovable.dev/mcp-js, Supabase OAuth)
  └─ /lovable/email/* (transactional email webhooks)
  ▼
Supabase (Postgres 17, RLS, SECURITY DEFINER RPCs, triggers, Storage buckets, Realtime, pg_cron for payment holds)
  ▲
External: Lovable AI gateway (Gemini), Lovable connector gateway (Firecrawl, Google Places), Google Maps JS, OneSignal push, PayPal Orders, Stripe (dormant), Meta Graph API (Content Studio)
```

The database is the enforcement boundary. Almost every minor-safety, payment and ownership rule exists as a trigger or RPC, and the SQL test suite asserts them. The client and server functions are convenience layers on top.

### 3.3 Architectural observations that shape the plan

1. **Three entity vocabularies for organizations.** `teams.kind` (team or coach), `trainer_orgs` (gym or facility), and `account_profiles.kind` (player, team, trainer, gym). "Org" in the client means a team or coach, while "org" in the database means a facility. A unified network needs one vocabulary before adding businesses.
2. **No generic event or post object.** Tryouts and camps are `team_posts`; facility events are `hosted_games` filtered by title; bookings are `trainer_session_requests`. Engagement already uses a polymorphic `subject_type`, which is the right seam to extend.
3. **Follows point only at people.** `follows.followee_id` references `auth.users`. Teams, facilities and trainers show a Follow button that does nothing.
4. **Realtime and data loading are store-centric.** Four singleton stores subscribe to whole tables. The games feed loads every unhidden game with `select("*")` and filters in JavaScript. This works at launch scale and will not scale with a network.
5. **Minor safety lives in SQL and is tested there.** `reel_audience`, `minor_messaging_block`, `enforce_game_join_gate`, `follow_approval_required`, `enforce_minor_privacy_floor` and friends are the assets to protect and extend; new surfaces must route through them.
6. **Governance debt is the top risk.** Production has drifted from the repo (71 unrecorded migrations, two merged but unapplied), Lovable applies SQL and pushes to main outside PR flow, E2E has not passed in two months, and a 25-PR youth-privacy stack is open with production marked NO-GO.

## 6. UX improvement recommendations

All findings are inferred from source, copy strings and route structure. Nothing was observed in a running browser.

### 6.1 Journey findings (Discover → Join → Play → Connect → Return → Invite)

- **Discover.** The landing promises "Find a game near me", but the Discover tab opens players' availability posts; games live under Home. `/discover` and `/pickup` already redirect to `/feed`. Signed-out previews are honest and labelled as samples.
- **Join.** A free, no-approval game is two taps from Home. Approval is the default when a game has no settings row, and after hotfix #287 strangers cannot read `requires_approval`, so every game shows "Request Spot" until PR #298 lands. A teen whose guardian is not linked is told "nothing to join or pay yet" with no link to fix it from the game page.
- **Play.** Game lifecycle, reminders, attendance and recap exist. Reminders fire only while the client is open. "Recap" in code means a highlight reel, not a game summary.
- **Connect.** Follow works for players; on team and trainer pages it is a local toggle that persists nothing and the Followers stat never changes. Posting is reachable only from a team page. Messaging is 1:1 only.
- **Return.** Last-visited restore and the NeedsActionStrip work. Home has no social content, so a player with no upcoming game has little reason to return.
- **Invite.** Share sheets and invite deep links with expiry are solid and covered by about twenty e2e specs.

### 7.3 Network entities (P1 and P2) with justification

Each proposed entity is listed with why an existing table is not enough, the migration plan, the RLS policies and the automated tests required. If the justification does not hold up in review, the entity should not be created.

**A. Polymorphic follow targets (P1).**
_Justification._ `follows.followee_id` references `auth.users`. Following a team, facility or trainer is the core network loop and cannot be expressed today; the team and trainer Follow buttons are fake.
_Plan._ Add `follow_targets(id uuid pk, kind text check (kind in ('user','team','org')), ref_id text, unique(kind, ref_id))` or add nullable `followee_team_id` and `followee_org_id` to `follows` with a check that exactly one target is set. The second option keeps the existing RPC family and is preferred.
_RLS._ Reuse `request_follow` and `respond_follow_request`: entity follows never need approval, person follows keep the minor approval rules. SELECT on entity follows limited to the follower and the entity owner.
_Tests._ Extend `110_follow_approval.test.sql`: teen following a team needs no guardian approval; following a hidden or unclaimed listing is refused; blocked user cannot follow the blocker's team.

**B. Network posts (P1).**
_Justification._ `team_posts` is team-scoped and its kinds are tryout, clinic, announcement, recap. Players, trainers and facilities need to publish, and the Home and Following feeds need one query.
_Plan._ Prefer generalising `team_posts` into `posts` with `author_user_id`, nullable `team_id`, `org_id`, `game_id`, `reel_id`, `kind` (`update`, `announcement`, `achievement`, `recap`, `tryout`, `clinic`), and `audience` (`public`, `followers`, `team`, `family`). Keep a `team_posts` view for compatibility during migration. Reuse `post_comments` and `post_reactions` by adding `post` to `subject_type`.
_RLS._ Author or team manager writes; read policy composes `audience` with `profile_visibility_of`, team membership, `is_guardian_of` and the existing moderation RESTRICTIVE policy. Minors' posts never public below 16 (same rule as `reel_audience`).
_Tests._ New `5xx_posts_audience.test.sql`: stranger cannot read a followers-only post; teammate can read a team post; under-16 post is never public; moderation hold applies; comment on a minor's post follows `can_comment_on_minor_content`.

**C. Events (P2).**
_Justification._ Three incompatible shapes today (team posts, hosted games with title regex, trainer sessions). Tryout registration, waivers and availability already exist and should be generalised rather than cloned.
_Plan._ `events(id, host_kind check in ('team','trainer','facility'), host_ref, kind check in ('tryout','clinic','camp','tournament'), starts_at, ends_at, venue (coarse for youth), lat/lng in a private table as the youth-privacy release does for games, price, capacity, waiver_id, moderation_status, hidden columns)`; `event_registrations` generalises `tryout_rsvps`; `event_availability` generalises `team_event_availability`. Backfill from `team_posts` where kind in (tryout, clinic); keep `/tryouts/$postId` as an alias.
_RLS._ Mirror the youth-game pattern: public rows carry coarse location; exact venue readable by registrants, guardians and host staff.
_Tests._ Port `150`, `160` style guardian tests to registrations; anon sees only adult-only events with exact venue.

**D. Coach identity (P2).**
_Justification._ A person coaching two teams has no cross-team identity; "trainer" is a bookable business profile, "coach" is a roster role.
_Plan._ Add `coach` to `account_profiles.kind` backed by `team_members.role in ('coach','manager','owner')`; no new table.
_Tests._ Account profile row appears and disappears with the roster role.

**E. Businesses (P2 or P3).**
_Justification._ The marketplace needs shops, physios, photographers and leagues. `trainer_orgs` already has category, hours, photos, claims, dual hide and reviews.
_Plan._ Expand `trainer_orgs.category` taxonomy and add `org_type check in ('facility','business')` rather than a new table. Extend `listing_claims.subject_type` and `reviews.reviewee_kind` with `business`. Extend the discovery engine's `subject_type` check.
_Tests._ Extend `70` and `80`; business review eligibility defined (verified visit or booking).

### 7.4 Performance migrations (P1)

- `CREATE INDEX hosted_games_sport_date_live_idx ON hosted_games (sport, date) WHERE hidden_at IS NULL;`
- Choose `earthdistance` (`cube` extension, already common on Supabase) or PostGIS for a `games_near(lat, lng, radius_mi, sport[], after, limit, cursor)` RPC that returns paginated rows under the existing RLS. Add a GiST index on `ll_to_earth(lat, lng)` or `geography`.

## 14. Specific recommended first implementation task

**Task: P0-2 "Close the two authenticated oracles and the role-escalation path."**

Why first: it is small (one migration, one SQL test file, two client call sites), independent of the 25-PR privacy stack, protects minors immediately, and exercises the exact branch, test, runbook and production-apply discipline that every later task will depend on. It can ship while the governance work in P0-1 is being approved.

Scope:

1. Migration `20261107120000_close_auth_oracles.sql`:
   - `REVOKE EXECUTE ON FUNCTION public.profile_ages(uuid[]) FROM authenticated;` add `public.profile_age_bands(_ids uuid[])` returning `(id, band text)` with the same visibility filter, where band is `adult`, `teen_16_17`, `teen_13_15` or `child`, and exact age only when `_ids` contains `auth.uid()` or the caller is a verified guardian or moderator.
   - `REVOKE EXECUTE ON FUNCTION public.minor_messaging_block(uuid,uuid) FROM authenticated;` add `public.minor_messaging_block_me(_other uuid)` that calls the original with `auth.uid()`.
   - `REVOKE INSERT, UPDATE, DELETE ON public.user_roles FROM authenticated;` drop policy `Admins manage roles`; add `public.grant_role(_user uuid, _role app_role)` and `public.revoke_role(...)` as SECURITY DEFINER requiring `is_superadmin(auth.uid())`, writing `admin_audit_log`; trigger `guard_user_roles_write` refusing any row change not made through those functions.
   - `lock_timeout`, `SET search_path`, allow-list entries.
2. SQL test `supabase/tests/500_auth_oracles.test.sql`: stranger gets band not age for a teen; guardian gets exact age; admin cannot insert superadmin; superadmin can via RPC with audit row; direct insert refused; `minor_messaging_block` direct call refused for authenticated, wrapper works.
